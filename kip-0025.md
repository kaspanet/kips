# Abstract

In the context of KIP-17 [[1]](#ref-1) and KIP-16 [[2]](#ref-2), which introduce Opcodes with non-trivial script
execution costs, this proposal introduces a more general resource-metering model for script validation. It defines
script execution costs for selected Opcodes through `ScriptUnits`, while preserving the existing compute-mass cost of
signature-check operations.

# Background

Transaction mass has three dimensions: compute mass, transient mass, and storage mass. In the legacy txv0 model,
compute mass is the sum of transaction-size mass, output script-public-key mass, and input signature-operation (sigop)
mass. Sigop mass is derived from the `sig_op_count` field of each input. This count is included in signature hashing
and serves as a per-input upper bound on the number of signature-check operations the spending script may execute. If
script execution attempts to exceed this bound, script validation fails and the transaction is rejected.

# Motivation

KIP-17 [[1]](#ref-1) and KIP-16 [[2]](#ref-2) introduce Opcodes whose validation cost is not tied to signature verification. The legacy txv0 sigop-based mass model only measures signature-check operations, so extending it to price general script execution would make the cost model less precise and harder to extend. For example, verifying a RISC Zero Succinct receipt is a proof-verification operation, not a signature check, and expressing its cost as sigop mass is no longer a practical abstraction.

This proposal introduces a generic script-execution cost model measured in `ScriptUnits`. For version 1 transactions, each input's committed `compute_budget` is converted into both compute mass and a per-input script-unit limit, allowing validation to price and bound signature checks, hashing, ZK precompiles, and other metered script work under a single execution-cost measure.

# Specification

Transaction inputs v0 MUST use the currently [existing sigops pattern](#background), while transaction inputs v1 MUST use the [proposed compute budget pattern](#compute-budget-grams-and-script-units).

## Compute Budget Grams and Script Units

For transaction version 1, each transaction input MUST include a `ComputeBudget` field, encoded as a `uint16`.

The `ComputeBudget` value denotes an abstract unit of computational allowance covered by the txv1 signature hash the full transaction hash [[3]](#ref-3).

One compute-budget unit is defined as exactly 100 compute script mass grams:\
 `ComputeScriptMassGrams = ComputeBudget × 100`

One compute-script-mass gram is defined as exactly 100 script units:\
`ScriptUnits = ComputeScriptMassGrams × 100`

An input script validation MUST fail if script execution consumes more than:\
`CommittedScriptUnits` + 9,999 SU\
where the first 9,999 SU are treated as a free allowance.

| Unit                    | Meaning                                                    | Current conversion          |
| ----------------------- | ---------------------------------------------------------- | --------------------------- |
| `ComputeBudget`         | The compact per-input commitment stored in the transaction | `uint16` units              |
| `ComputeScriptMassGram` | Compute mass unit used by mass accounting and fees         | `1 budget = 100 grams`      |
| `ScriptUnits`           | Runtime script execution meter                             | `1 gram = 100 script units` |

By introducing `ScriptUnits`, this proposal increases script metering granularity by a factor 10 relative to txv0 sigop-mass grams.

## Cost Design

### Hashing Opcodes

| Opcode | Name             | Script unit count         |
| ------ | ---------------- | ------------------------- |
| 0xa8   | OP_SHA256        | 1 SU per hashed byte      |
| 0xa7   | OpBlake2bWithKey | 2 SU per hashed data byte |
| 0xaa   | OpBlake2b        | 2 SU per hashed byte      |
| 0xd9   | OpBlake3         | 1 SU per hashed byte      |
| 0xda   | OpBlake3WithKey  | 1 SU per hashed data byte |

### ZK Opcode

Cost depends on the proof-system variant selected by `tag` [[2]](#ref-2).
| Opcode | Name | Script unit count |
| ------ | ---------------------------- | ----------------------------- |
| 0xa6 | OpZkPrecompile (Groth16) | 14,000,000 SU + 250,000 SU × (number of public inputs [[2]](#ref-2) + 1) |
| 0xa6 | OpZkPrecompile (RISC Zero Succinct) | 25,000,000 SU |

Costs have been determined empirically [[5]](#ref-5) using benches [[4]](#ref-4) with the goal of keeping execution below ~10ms.

### Script Engine Event

| Script Engine Event                           | Script unit count                    |
| --------------------------------------------- | ------------------------------------ |
| Bytes pushed into script stack                | 1 SU per newly pushed bytes          |
| Spent UTXO SPK above standard size (35 bytes) | 100 SU per byte above limit (1 gram) |

Bytes newly pushed into the data stack - existing stack bytes are not charged again when they remain on the stack, but duplicated or newly produced stack entries are charged.

### Signature Check Opcodes

Each signature verification attempt consumes 100,000 SU:

| Opcode | Name                     |
| ------ | ------------------------ |
| 0xa9   | OpCheckMultiSigECDSA     |
| 0xab   | OpCheckSigECDSA          |
| 0xac   | OpCheckSig               |
| 0xad   | OpCheckSigVerify         |
| 0xae   | OpCheckMultiSig          |
| 0xaf   | OpCheckMultiSigVerify    |
| 0xd7   | OpCheckSigFromStack      |
| 0xd8   | OpCheckSigFromStackECDSA |

For `MultiSig` Opcodes, the cost is per cryptographic verification attempt (for each signatures to check).

Note: This proposal maintains the same amount of `ComputeScriptMassGrams` per signature check as currently implemented (1,000).
